## 3. Rendimiento — RNF-04 (con 200 entradas)
**Entorno de medición:** Pixel 6 / API 35 (emulador, 4 GB), fixture `fixtures/many-launchers` (paquete `com.focuslauncher.fixture200` con **200 `activity-alias` launcher** con acentos) más las apps del sistema. APK release **real** (R8, no depurable, 3,0 MB, firmado con la clave de depuración local; nunca se distribuye). **Es un emulador, no el Pixel 6 físico.**

| Carga del catálogo real de 200 entradas | 20 | 10,1 ms | 23,0 ms | 24,2 ms | (informativo) | — |
| Derivación del PIN (PBKDF2-HMAC-SHA256, 600000 it.) | 7 (+1 calentamiento) | 342 ms | — | 345 ms (mín. 334) | indicador si > 300 ms | Supera 300 ms ⇒ el indicador **sí aparece** (por diseño, ya implementado en T07) |

Cómo se midió y sus límites:
- **Arranque**: `reportFullyDrawn()` se llama cuando Inicio muestra su primer contenido útil (lista, vacío o bloqueo explícito); el tiempo lo anota el sistema (`ActivityTaskManager: Fully drawn`). No añade registros propios.
- **Búsqueda, cambio de visibilidad y catálogo** (`PerformanceBudgetTest`): se ejecutan con el tipo de compilación `benchmark` (activable con `-PperfBuild=true`): como release —**no depurable**, sin sobrecoste de depuración— pero **sin R8**, porque R8 elimina de la app clases que necesita el APK de pruebas instrumentadas. El arranque frío sí se midió con R8. El «cambio de visibilidad» mide hasta que la lista visible lo refleja (no incluye el siguiente fotograma de pantalla).
- El arnés de pruebas de Compose (`performTextReplacement` + `waitForIdle`) cuesta por sí solo ~400 ms sobre un campo vacío, por eso la búsqueda se mide cambiando la consulta del ViewModel y esperando a que la UI quede estable (línea base del procedimiento: 16,7 ms ≈ un fotograma, incluida en las cifras).
- Variación: en depuración el mismo benchmark da una búsqueda de p95 ≈ 133–153 ms; la diferencia con release es el sobrecoste de Compose en depuración.

## 5. Auditoría del manifiesto combinado (RNF-05) y defectos hallados
El manifiesto del **APK release real** (`aapt2 dump`) mostró algo que la prueba de higiene sobre el manifiesto *fuente* no ve: una dependencia (`androidx.profileinstaller`) aportaba un **`ProfileInstallReceiver` con `exported=true`** y 4 acciones (protegido por el permiso `DUMP`, es decir, solo shell/sistema). Focus no incluye baseline profile y la regla del proyecto es no exponer receivers: **se eliminó** con `tools:node="remove"`. Además:
- Nueva tarea **`./gradlew :app:verifyReleaseManifest`** (se ejecuta tras `assembleRelease`): falla si el manifiesto combinado tiene un permiso fuera de la lista (hoy solo el permiso interno de AndroidX), cualquier `receiver`/`service`, un `provider` sin `exported=false`, más o menos de una actividad exportada, `debuggable`, tráfico en claro, `allowBackup` distinto de `false`, falta de `dataExtractionRules` o `<queries>` más amplias que el intent MAIN/LAUNCHER. Probada con una mutación (receiver exportado + `INTERNET`): falla.
- Resultado actual: **1 permiso** (`DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`, propio de AndroidX), 0 receivers/services, 1 provider no exportado (`androidx.startup`), 1 actividad exportada, sin `INTERNET`, `QUERY_ALL_PACKAGES` ni `ACCESS_HIDDEN_PROFILES`.

Otros defectos y correcciones de T10:
1. **Búsqueda lenta en la lógica** (hallazgo de la medición): normalizar los 200 nombres con `Normalizer` + expresión regular en *cada pulsación* costaba **p50 10,6 ms / p95 34,6 ms**; ahora el índice se construye una vez por lista (1 ms) y cada consulta cuesta **p50 0,04–0,16 ms**.
2. **El motor ATF no funciona en API 31** (lo detectó la prueba guardia): las 72 pruebas ATF se omiten en API < 34 en lugar de «pasar en vacío».
3. **API 31/32**: `dumpsys` no tiene `topResumedActivity` (usa `mResumedActivity`) y «Atrás» ya no cierra la actividad raíz (comportamiento estándar de Android 12): el helper de pruebas lo contempla.
4. Faltaba un punto de medición de arranque: `reportFullyDrawn()` (sin registros propios).
